## Executive Finding

The Sensei cron skill-loader issue is likely caused by `tools.skills_tool` capturing `SKILLS_DIR` at module import time.

When the long-running cron/gateway process has already imported `tools.skills_tool` under the default profile, `SKILLS_DIR` remains pointed at:

```text
C:/Users/tophe/AppData/Local/hermes/skills
```

Even after the cron scheduler enters the Sensei profile context, `skill_view()` continues searching the default profile skill directory instead of:

```text
C:/Users/tophe/AppData/Local/hermes/profiles/sensei/skills
```

That explains why the cron job reports:

```text
Skill(s) not found and skipped: word-explainer, lesson-history
```

even though those skills exist and are enabled in the Sensei profile.

## Root Cause Assessment

Likely root cause:

```text
PROFILE_CONTEXT_IMPORT_TIME_SKILLS_DIR_CAPTURE
```

Plain-English explanation:

```text
The cron scheduler correctly enters the Sensei profile context, but the skill-view tool appears to use a skills directory constant that was captured earlier when the process was still using the default profile. Because the default profile does not contain `word-explainer` or `lesson-history`, the cron job skips them.
```

Confidence:

```text
High
```

Why high:

- Sensei CLI profile sees the skills.
- Default profile does not.
- Cron warning matches default-profile visibility.
- Source code uses module-level `SKILLS_DIR`.
- Isolated read-only check reproduced the stale `SKILLS_DIR` behavior.

## Impact

If left unfixed:

- Sensei cron may continue running without its intended profile-local skills.
- Even after model quota is fixed, the job may still start with a warning and reduced teaching context.
- Other profile-scoped cron jobs that depend on profile-local skills may have the same issue if those skills are not also present in the default profile.

## Repair Options — Not Executed

No repair was performed.

### Option A — Code fix: make skills directory resolution dynamic

Preferred long-term engineering fix.

Potential direction:

```text
In tools/skills_tool.py, replace module-level static SKILLS_DIR use with a function that resolves `get_hermes_home() / "skills"` at call time.
```

Example conceptual direction only:

```text
def _skills_dir():
    return get_hermes_home() / "skills"
```

Then `skill_view()`, `skills_list()`, and helper functions should use the dynamic directory instead of the import-time constant.

Requires:

- Igris/Codex engineering work card.
- Tests for profile-context cron skill loading.
- Tusk QC.
- Chris approval.

### Option B — Cron scheduler workaround

Potential direction:

```text
Delay importing tools.skills_tool until inside profile context and ensure the module has not already captured default SKILLS_DIR, or explicitly refresh/reload skill resolution state under the profile context.
```

Risk:

- Module reloads in a long-running process may have side effects.
- Less clean than dynamic path resolution.

### Option C — Duplicate Sensei skills into default profile

Not recommended except as a temporary workaround.

Why not:

- Duplicates profile-local skills into default scope.
- Increases drift risk.
- Violates clean profile isolation.

### Option D — Remove skills from cron job and rely on prompt only

Not recommended.

Why not:

- Silences warnings but loses reusable skill governance/history behavior.
- Does not fix the underlying profile-local skill loading issue.
